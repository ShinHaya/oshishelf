# MVPの開発手順

## ローカル環境

Node.js 22（22.12以上）と `package.json` の `packageManager` に指定したpnpmを使います。
DockerとCIもNode.js 22に揃えています。

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm check
pnpm build
```

検査とビルドにはクラウドの認証情報は不要です。
ただしFirebaseの公開設定と`GOOGLE_CLOUD_PROJECT`を同じ環境の値で設定します。
CIでは架空の公開設定を使います。
Next.jsの型は `pnpm typecheck` が `next typegen` で生成するため、初回に開発サーバーを起動する必要もありません。

画面から認証、保存、AI生成を試す場合は、Firebase Authentication、Firestore、Vertex AIが利用できる開発用Google CloudプロジェクトとADCが必要です。

```bash
cp .env.example .env.local
# .env.local の GOOGLE_CLOUD_PROJECT を開発用プロジェクトに変更
gcloud auth application-default login
pnpm dev
```

`APP_ORIGIN` はローカルでは `http://localhost:3000` にします。
モデルとリージョンの設定は `.env.example` に記載されています。
cronのOIDC設定とアフィリエイト設定は、その機能を確認するときだけ設定します。
`.env.local`、サービスアカウント鍵、ADCの内容はコミットしません。

Firebase Web設定は`NEXT_PUBLIC_FIREBASE_*`の4変数で指定します。
`GOOGLE_CLOUD_PROJECT`と同じプロジェクトの値を使い、Authenticationのログイン方式とlocalhostの承認済みドメインも確認してください。
公開設定はビルド時にブラウザのコードへ埋め込まれるため、実行時の環境変数の変更だけでは切り替わりません。
プロジェクトの不一致はビルド時とサーバー起動時に拒否します。
Web設定は公開情報ですが、サービスアカウント鍵とは別物です。
新規ステージングの構築とActionsの設定は[構築手順](staging.md)を参照してください。

Firestoreのルールとインデックスは `scripts/setup-firestore.sh` を参照してください。
このスクリプトと `scripts/seed.mts` はクラウドの状態を変更するため、対象プロジェクトと内容を確認してから実行します。
MVPの現状では、エミュレーターによるアプリ全体の起動は整備していません。

## 検査コマンド

| コマンド | 用途 |
| --- | --- |
| `pnpm lint` | ESLint。警告も失敗として扱う |
| `pnpm typecheck` | Next.jsの型生成とTypeScriptの検査 |
| `pnpm test` | 外部通信なしの回帰テストを一度実行 |
| `pnpm test:watch` | 編集中のテスト再実行 |
| `pnpm check` | Lint、型検査、テストを順に実行 |
| `pnpm build` | 本番ビルドが成立するか確認 |

## テストの追加方針

テストは対象の近くに `*.test.ts` として置き、VitestのNode環境で実行します。
まず公開範囲、成人向けAI入力、商品URL判定、SSRF対策など、誤ると情報漏洩や誤取り込みにつながる条件を検査します。
テストデータは架空の作品とユーザーを使い、FirebaseやGeminiを実際に呼び出しません。
不具合を修正するときは、その入力と期待する結果を回帰テストに残します。

`server-only` を読み込むモジュールは、対象のテスト内で `vi.mock("server-only", () => ({}))` を使い、外部通信もモックします。
このモックをアプリ本体に持ち込まないでください。
非同期Server Componentsはこの単体テストの対象にせず、画面の確認で検証します。
認証やFirestoreの実動作、AI出力品質を単体テストの成功だけで確認済みにしないでください。

## レビューとマージ

1. 作業ブランチで実装し、必要な回帰テストを追加する。
2. `pnpm check` と `pnpm build` を実行する。
3. 人間またはAIが `git diff` を読み、下記の項目を確認する。
4. 指摘を修正したら影響する検査を再実行し、PRテンプレートに結果と未確認の範囲を記載する。
5. CIの `check` が成功し、未解決の不具合がないことを確認してマージする。

継続開発のPRは`develop`へ向け、完了するIssueをPR本文の独立した行に`Closes #123`と記載します。
複数の場合は行を分けるか、`Closes #123, #124`と記載します。
参照だけのIssueは`Related #123`とし、完了していないIssueにclosing keywordを使いません。
[GitHub標準の自動クローズ](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)は既定ブランチへのマージだけが対象です。
mainの凍結は2026年10月15日23:00（日本時間）から開始し、それまでは利用者の指示によりmainも更新できます。
凍結後も既定ブランチ`main`を維持するため、`Close merged issues` Actionsが`develop`へのマージ後に明示的なclosing行を処理します。
マージせず閉じたPR、他ブランチ宛てのPR、コードブロックやコメント中の例、別リポジトリのIssueは処理しません。
Actionsが失敗した場合は実行ログと関連Issueの状態を確認し、原因を直して再実行します。

レビューでは、変更の目的と挙動が一致しているか、未ログインや非所有者からの操作が拒否されるか、下書きや制限付き作品が画面とAI出力へ漏れないかを確認します。
成人向けの変更では所有者のAI利用同意と閲覧者の表示同意を別々に確認します。
外部URLの変更ではSSRFとリダイレクト、AIの変更では入力の制限と利用上限、データ削除の変更では関連データの削除範囲を確認します。

AIにレビューを依頼する場合は、次の依頼文を使えます。

```text
AGENTS.mdとdocs/development.mdを読んで、現在の差分をレビューしてください。
実際に起きる不具合、認証と公開範囲、成人向けAI入力、外部URL、費用、回帰を確認してください。
指摘にはファイル位置、発生条件、影響、修正案を記載してください。
コードは変更せず、指摘なしの場合も未確認の範囲を記載してください。
```

CIはPRとmainへのpushで検査とビルドを実行します。
クラウドのsecretや自動デプロイは使いません。
ブランチ保護はリポジトリ管理者がGitHubで設定する必要があり、このファイルを追加するだけではマージを強制的に制限できません。
必要ならmainの必須ステータスチェックに、このCIの `check` を指定してください。

## 画面変更時の手動確認

変更に関係する項目だけを開発用プロジェクトで確認し、PRに対象と結果を記載します。

- 認証：未ログインの保護ページ、ログイン、ログアウト後のアクセス。
- 取り込み：架空の商品を取り込み、下書きで保存され、本人の確認後に公開されること。
- 公開範囲：所有者、フォロワー、非フォロワーで棚と購入リンクの見え方を確認すること。
- 成人向け：表示OFFで作品が隠れ、AI利用同意OFFで成人向けの情報を使わないこと。
- AI：下書き生成と承認を確認し、エラー時にも既存データが失われないこと。
- 退会：専用の使い捨てユーザーで関連データの削除を確認すること。

新たな不具合が繰り返される操作は、必要になった時点でE2Eテストに追加します。
MVPでは全画面のE2Eや一律のカバレッジ目標は設けません。

## AI利用量の上限

上限はUTCの日付単位で、失敗した処理も消費量を戻しません。
取り込みは解析前に回数枠、商品ページの取得前に候補件数枠を予約します。
検索リンクのみの候補と重複候補も件数に含みます。
候補件数枠を超える場合、その候補の外部取得と保存は開始しません。
解析済みでも件数枠で拒否されることがあるため、件数を減らして再実行してください。

| 対象 | ユーザーの日次上限 | サービス全体の日次上限 |
| --- | ---: | ---: |
| 取り込み候補 | 300件（Auth作成から7日未満は50件） | 3,000件 |
| テキスト・ブックマークレット解析 | 40回 | 200回 |
| スクリーンショット解析 | 15枚 | 100枚 |
| Geminiの商品情報フォールバック | 10件 | 100件 |
| 自己紹介 | 10回 | 100回 |
| 相性分析 | 30回 | 300回 |
| 分身チャット | 60回 | 600回 |
| 手動ウォッチャー | 5回 | 50回 |

Geminiの商品情報フォールバックは1回の取り込みにつき最大5件です。
この枠がない場合はページやカードから得た情報だけで下書きを作成します。
スクリーンショットも解析枠に加えて取り込み候補枠を消費します。
ユーザー枠と全体枠はFirestoreの同一トランザクションで予約し、並行リクエストでも上限を適用します。
全体枠は `globalUsage` に保存し、退会時も削除しません。
これらは処理量の上限であり、トークン数や課金額そのものの上限ではありません。
