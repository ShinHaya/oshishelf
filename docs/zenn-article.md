## 購入作品を通じて趣味の仲間とつながる

**推し棚（OshiShelf）** は、複数のショップで買ったマンガ、書籍、ゲームを「棚」にまとめて共有するSNSです。
楽天ブックス、Amazon、Steamなどに分散した購入作品から、公開してよい作品を本人が選びます。
フォローした人の棚で気になった作品は、購入リンクから商品ページへ進めます。

![推し棚のトップページ](https://static.zenn.studio/user-upload/692fd29030a7-20261014.png)

購入履歴は趣味を表す記録ですが、ショップごとに閉じています。
手入力で何十冊も登録するには時間がかかり、履歴には健康や金融、贈り物など、人に見せたくない商品も混ざります。
趣味の合う人を見つけても、最初に何を話すか迷うことがあります。

そこで、棚づくりから交流までを6つのAIの役割で支援しました。
取り込みとプライバシーガードはGeminiの構造化出力によるパイプラインで、プロフィール、相性分析、AI分身、ウォッチャーの4つはADKのツール使用エージェントです。

## 棚づくりから交流までの体験

1. 購入履歴ページのブックマークレット、テキスト、商品URL、スクリーンショットから作品を取り込む。
2. 下書きになった作品を確認し、公開する作品と公開範囲を本人が選ぶ。
3. 公開棚をもとにAIが自己紹介を下書きし、本人が編集して承認する。
4. 趣味の近い人を見つけ、相性分析から共通点や話しかけ例を読む。
5. フォロー相手のAI分身におすすめを聞き、回答中の作品リンクから商品ページへ進む。
6. 「ほしい」に登録した商品の価格と、好きなジャンルの新作をウォッチャーに調べてもらう。

## 購入履歴を読み、公開前に確認する

購入履歴ページの読み取りは、ユーザー自身のブラウザで動くブックマークレットが行います。
ショップのログイン情報を推し棚へ預ける必要はありません。
ページ上の商品リンク、周辺テキスト、見出し、画像候補を集め、推し棚のウィンドウへ渡します。
自動スクロールと同一サイト内のページ送りも行います。

取り込みエージェントは、購入済みの作品とおすすめや広告を区別し、重複したリンクをまとめます。
AIが返したURLと画像は、ページ上に実在する候補だけを採用します。
商品らしいのに選ばれなかったリンクは、見落とし候補として再確認します。
架空のAmazon風注文履歴では2ページの7件、本棚の無限スクロールでは5件を取り込めましたが、実購入履歴や全ショップでの精度を保証する結果ではありません。

取り込んだ作品は下書きとして保存します。
プライバシーガードは健康、金融、ギフト、個人情報、年齢制限などの観点から公開範囲を提案し、要確認の商品は選択を外した状態で表示します。
2026年10月13日の架空履歴3件による確認では、借金返済に関するサンプル1件が要確認になりました。
公開対象に含めるには本人の操作が必要です。

## 公開棚を調べるエージェント

プロフィールエージェントは、ADKのツールで公開棚を探索して自己紹介を下書きします。
棚全体の傾向、カテゴリ別の作品、キーワード検索を使い、どのツールを呼んだかは「エージェントの行動ログ」に表示します。
生成しただけでは公開せず、本人の編集と承認を挟みます。

相性マッチングは、作品とタグをgemini-embedding-001でベクトル化し、Firestoreのベクトル検索で趣味の近い人を推薦します。
プロフィールでは、2人の公開棚を比較して相性スコア、共通点、おすすめ作品、話しかけ例を生成します。

AI分身は、フォロー相手の全体公開の棚を検索しておすすめを答えます。
回答中の作品IDはコードで棚との一致を検証し、採用した作品に購入リンクを付けます。
分身がAIであることも画面に明示します。

![相性分析とAI分身チャット](https://static.zenn.studio/user-upload/e9b3250ec563-20261014.png)

## 巡回の判断と事実確認を分ける

ウォッチャーは「ほしい」の商品価格を確認し、Google検索グラウンディングで新作を調べ、最近の通知との重複を確認して通知します。
手動起動に加え、Cloud SchedulerからOIDC認証付きで起動する定期巡回も実装しています。
今回確認したのは手動起動で、実際の定期起動時刻や継続的な実行履歴は未確認です。

開発中には、価格が変わっていない商品をモデルが値下がりとして通知することがありました。
そこで、価格比較はコードが行い、確認できた値下がりだけ通知ツールが受け付けるようにしました。
巡回結果の要約も、モデルの自己申告ではなくツールの実行回数から作ります。

1回の巡回は検索2回、値下がり通知3件、新作通知2件までに制限しています。
ツール呼び出しの履歴はFirestoreのagentRunsへ保存します。

以下は撮影時の画面例で、10月13日の確認とは別の巡回です。
通知内の発売日は未検証です。

## 公開範囲と成人向け同意を守る設計

書き込みはサーバーで認証と所有者を確認し、Firestoreへのクライアント直接アクセスは拒否します。
下書き、非公開、フォロワー限定の作品は公開向けAI入力から除外します。
既存の相性キャッシュには公開範囲変更後の表示に制限があり、修正実装の本番反映は未確認です。

他の人の成人向け作品を表示するには、閲覧者の18歳以上の申告と表示同意を要求します。
成人向け作品のAI利用には、所有者の別の同意が必要です。
AIにはジャンルとタグだけを渡し、タイトル、画像、URL、メモは伏せます。
自己紹介は成人向けの傾向を含む版と含まない版を用意し、閲覧者の設定に応じて表示します。
相性分析と分身の入力も同意に応じて切り替え、出力は非露骨な表現に限定します。
この組み合わせの実ブラウザ検証は未実施です。

ユーザー指定URLの取得は、安全確認を行う共通処理を経由します。
HTTP(S)に限定し、DNS解決後のプライベートIPを拒否して、リダイレクト先も再検証します。
取得サイズと時間を制限し、モデルが返したIDやURLにもコード側の検証を挟みます。

## Google Cloud上の構成

![システムアーキテクチャ](https://static.zenn.studio/user-upload/85726f1bf0bc-20261014.png)

| 役割 | 使用技術 |
| --- | --- |
| アプリ実行 | Cloud Run、Next.js 16 App Router、Server Actions |
| ツール使用エージェント | Agent Development Kit（@google/adk、TypeScript） |
| 生成AI | Vertex AI、Gemini 2.5 Flash / Flash-Lite |
| 埋め込みと検索 | gemini-embedding-001、Firestoreベクトル検索 |
| 外部情報の参照 | Google検索グラウンディング、URL Context |
| データ保存 | Firestore（サーバー経由） |
| 認証 | Firebase Authentication、httpOnlyセッションCookie |
| 定期起動 | Cloud Scheduler、OIDC検証 |

ツール探索とスキーマ付きの整形は分けています。
エージェントの最終回答がJSONとして解釈できないときは、ツールの実行結果を添えたスキーマ制約付きの整形呼び出しへフォールバックします。

AI利用は機能ごとにユーザーとサービス全体の日次上限を設け、失敗した処理も使用量として数えます。
Geminiの429応答には指数バックオフで再試行します。
日次上限は処理回数の制限であり、課金額そのものの上限ではありません。

## 確認できたことと残る範囲

2026年10月13日に、共有デモアカウントと架空履歴で一般向けの操作を確認しました。
取り込み3件は下書きになり、要確認1件は未選択でした。
未ログインの非所有者には、非公開、フォロワー限定、下書きの作品が棚と購入リンクから隠れることを確認しました。
自己紹介は承認前に公開内容を変えず、承認後に反映されました。
相性分析、公開棚からのAI分身の回答、手動巡回の行動ログも確認しています。
手動巡回は価格確認2件、値下がり0件、新作通知2件でした。

各ショップの実購入履歴、スクリーンショット経由の取り込み、フォロワーとしてログインした別アカウントの閲覧、成人向け同意を有効にした複数アカウントの実ブラウザ検証、定期巡回は今回の通し確認に含めていません。
新作通知の発売日の正確性も未確認です。
認証、購入リンク、相性キャッシュなどの安全性修正はローカル検査済みですが、本番反映と実クラウドでの確認は未実施です。
詳細は[操作手順と確認記録](https://github.com/ShinHaya/oshishelf/blob/main/docs/demo-validation.md)に記載しています。

## 今後の改善

購入履歴の取り込み精度と新作通知の発売日検証を改善し、作家やシリーズ単位でも作品を追えるようにしたいと考えています。
棚を通じた作品の発見が、同じ趣味の人との交流につながるかも検証していきます。

購入履歴は本人の「好き」の記録です。
その記録を棚にまとめる作業はエージェントが支援し、何を公開するかは本人が決める。
推し棚では、この役割分担を体験と実装の両方で形にしました。
